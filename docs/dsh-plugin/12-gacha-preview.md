# 12 · 二游前瞻来源（`@lidozs55/dsh-schedule-gacha`）

> 一句话：只读 B 站官方公告与官方视频，为六款二游各维护**「版本前瞻直播」与「版本更新」两条日程**；
> 其余日程一概不碰。

插件位置：`dsh-plugin/dsh-schedule-gacha/`，row id `gacha-schedule`，
`inject: ['scheduleCore', 'connection', 'tools']`。数据真相仍在核心
`@lidozs55/dsh-schedule`（日程条目 + `sourceState.gacha`），本插件只是来源适配器
（契约见 `11-source-plugins.md`）。

## 3. 数据源与实测前提（2026-10-21）

所有请求匿名进行，**不需要登录**；`x/frontend/finger/spi` 取一个匿名 `buvid3` cookie。

| 端点 | 用途 | 关键前提 |
|---|---|---|
| `x/space/article?mid=&pn=1&ps=30&sort=publish_time` | 官方专栏列表 | `Referer: https://space.bilibili.com/<mid>/article`；返回的 `summary` 只有 255 字符，但维护时刻都在其中，崩铁/绝区零的版本结束日也在其中 |
| `x/article/view?id=` | 专栏全文 | 限流严格（连发 `-509`）；串行间隔 ≥2.8 s，仅在摘要不足时调用 |
| `x/series/recArchivesByKeywords?mid=&keywords=前瞻` | 官方合集视频 | **必须**用 `https://space.bilibili.com/<mid>/upload/video`，否则 HTTP 412；鸣潮只能靠这条 |
| `x/web-interface/search/type?search_type=video&...` | 搜索兜底 | `Referer: https://search.bilibili.com/`；按 `mid` 过滤官方号 |
| `x/polymer/web-dynamic/v1/feed/space?host_mid=` | 官方动态 | 不稳定（常见空列表 / `-352`），只作可选公告来源，失败不阻塞 |
| `x/web-interface/view?bvid=` | 视频详情 | 目前只在手动排查时使用 |

不可用：`x/space/wbi/arc/search`（`-352`）与 `x/space/arc/search`（`-799`）；
不做 WBI 签名，避免风控改动直接把插件打挂。

`bilibili.js` 用一个全局串行链（按出口 IP 限流，而不是按端点）：
普通列表 1.2 s 间隔，合集/动态 2.5 s，全文 2.8 s；`-509/-799/-352/412` 退避重试并
刷新匿名 cookie，仍失败则抛 `BiliError`，**调用方保留上一次成功状态，绝不写猜测值**。

## 4. 刷新流程（每款游戏）

1. 拉官方专栏列表，用标题正则挑出**最新的“版本更新说明/公告”**（排除补偿、优化、FAQ 等）。
2. 若文章 id 与上次相同，跳过解析（省一次全文请求和一次 PV）。
3. 先用列表里的 `summary` 解析：维护开始、维护结束、版本号/版本名、版本结束日。
4. **摘要优先合并**：仅当摘要缺少更新时间、版本号，崩铁/绝区零缺少版本结束日，或终末地
   缺少阶段更新日时，才拉全文；全文只补摘要没有的字段，不覆盖摘要已确认的 `updateStart`。
   > 终末地全文开头是**上一阶段**的 `2026/10/22 04:00` 维护时间；若用全文覆盖，会把
   > `updateStart` 改错。摘要里的 `2026/10/15 06:00` 必须保留。
5. 找官方前瞻视频：官方合集 → 搜索 `<游戏名> 版本前瞻特别节目` → 搜索兜底关键词；
   过滤“场景前瞻/角色前瞻/前瞻短片/前瞻PV/预告片/实录”，只保留真正的版本前瞻节目。
6. 拉最近 75 天的官方动态（可选），用于“X.Y 版本前瞻将于…播出 / 将于…更新”这类明确公告。
7. `planNext` 纯规则算出下一版本的前瞻与更新时间。
8. 对账：每款游戏最多两条核心条目；多余的本插件条目删除，用户手工条目不动。

后台每 6 h 跑一轮；设置卡“立即刷新”和 Agent `refresh` 走同一队列，不会并发抓取。

## 5. 推算优先级

### 更新时间（下一版本）

1. 官方“版本结束时间 / 版本持续时间” → `official`
2. 终末地公告中 21–35 天后的“阶段内容更新” → `inferred`（证据可追溯）
3. 官方动态/公告中的“下一版本将于…上线/更新” → `official`
4. 当前更新时间 + 42 天，并对齐到同一星期几 → `inferred`
5. 若推出来的版本维护已结束，继续向后滚动（最多 16 次）

### 前瞻直播

1. 官方动态/公告/视频标题中明确写出的日期时间 → `official` / `video`
2. 官方前瞻视频回推：
   - 标题写明“将于 10 月 6 日 19:30 播出” → 直接用标题时间；
   - HoYo：发布日前最近的周五 19:30（录像次日上传）；
   - 鸣潮/终末地/异环：发布日 19:30；
3. 规则：更新时间前 8–14 天内的那个周五 19:30 → `inferred`
4. 兜底再校验：前瞻必须早于更新时间，否则回到第 3 条

所有日期按公告的 `UTC+8` 解释，落库为显式 `+08:00` ISO 字符串，**不依赖宿主时区**。

已覆盖的公告写法（离线测试用例）：

- 崩铁：`■更新时间 2026/09/28 06:00` + `4.6版本的持续时间为 … - 2026/11/11 06:00`
- 原神：`〓更新时间〓 2026/09/23 06:00`（无结束日 → 42 天）
- 绝区零：`【更新开始时间】 …` + `3.2版本结束时间为 2026/10/21 06:00`
- 鸣潮：`✦更新维护时间：2026年9月30日04:00 ~ 2026年9月30日11:00（UTC+8）`
- 终末地：`2026/10/15 06:00 - 2026/10/15 12:00（UTC+8）` + 后文 `2026/11/12 12:00` 阶段更新
- 异环：`9月24日06:00 – 11:00 进行版本更新维护`

样例 opus `https://www.bilibili.com/opus/1252891786169286742` 是崩铁 4.6 更新说明；
其专栏同文（`cv53199726`）的列表摘要已包含 `2026/11/11 06:00` 的版本结束时间，
因此不用拉全文就能得到下一版本更新日 **2026-11-11**（实测见 §9）。

## 6. 日程条目的归属

每条描述第一行带两个标记：

```
[gacha:<game>][kind:preview] 由「二游前瞻」插件自动维护，请勿手动修改时间。
[gacha:<game>][kind:update]  同上
```

- 只认这两个标记：列表、删除、对账都以此判断“是不是本插件写的”。
- `category: 'other'`；写入带 `allowConflicts: true`，与课程/考试冲突时由用户自行取舍。
- 标题形如 `原神 7.2 版本前瞻直播` / `明日方舟：终末地 版本更新`（终末地无数值版本号）。
- 描述写明版本、依据、维护时段、公告链接；推算值带“（推算）”。
- 前瞻已过去 2 天以上就不再创建；更新维护结束后条目保留在历史里，下次刷新滚动到新版本。
- 关闭某游戏：删除该游戏的两条标记条目，状态变 `disabled`，不再请求其接口。

## 7. Agent 工具 `gacha_schedule`

唯一写入口是 `service.applyOfficial`：**只接受游戏 id + 明确时刻**，没有“任意条目 id”参数，
因此 Agent 在结构上改不到用户的其他日程。

| action | 参数 | 行为 |
|---|---|---|
| `list` | — | 六款游戏的状态、版本、更新时间、前瞻时间、依据、公告链接 |
| `refresh` | `game?` | 入队刷新；返回每款游戏的结果 |
| `apply_official` | `game` + `update_start` / `preview_start`（`+08:00` ISO）+ 可选 `update_end`、`preview_end`、`version`、`note` | 写成 Agent 覆盖层；`clear: true` 清除覆盖回到公告规则 |
| `watch` | `watch_enabled`（默认 `true`） | 用 `ctx.schedule` 登记/取消每周三 10:00 的 Agent 核对 |

覆盖层规则：

- 覆盖优先于规则结果，但**新公告晚于覆盖时间**时自动失效（避免旧修正压住新事实）。
- 只写一个时间也可以：另一个沿用规则；维护结束时间缺省按游戏惯例窗口补。
- 校验：`update_end > update_start`、`preview_end > preview_start`、`preview_start < update_start`。

`watch` 依赖可选的 `ctx.schedule` bundle：缺失时工具返回降级说明，6 小时后台刷新照常，
`needsRefresh()` 也照常工作。周检 prompt 明确要求先 `list`、再逛官方账号、最后按游戏写回。

`index.js` 还给 `systemPrompt` 注入一段说明，提醒 Agent 不要用 `sched_entry` 改这些条目。

## 8. 设置卡

`client.settings.js` 注册进核心的 `schedule.settings.blocks`（`order: 20`），不新开页面：

- 六行游戏开关 + 每行的版本/更新/前瞻摘要，推算值前加 `≈`。
- “立即刷新”只触发后台 worker，卡片轮询 `refreshing`，结束后广播 `schedule:data-changed`。
- “让 Agent 核对”创建普通会话并投递核对 prompt，再打开工作区；不另造 Remote 端点。
- 底部显示上次刷新时间与周检状态；失败信息就地展示，不用弹窗。

关闭开关只影响该游戏；核心设置页的其他卡片不受影响。

## 10. 日志

宿主日志中所有行都以 `gacha-schedule:` 开头，按阶段记录，不输出公告正文：

- `x refresh start (article=…)` → `article list: N rows` → `picked article <id> "标题"（CST 发布时间）`
- `summary parse: version=… update=…→… versionEnd=… | summary sufficient`，或
  `| full text needed（缺更新时间、缺版本结束日…）`
- `full column merged: …`（仅在确实拉了全文时出现）
- `preview videos=N, recent dynamics=M`
- `plan <版本>: update …（依据）, preview …（依据）`
- `entry preview/update created|updated|unchanged: <id> …`
- `x refresh ok|partial|error in N ms`

端点级明细（GET 路径、耗时、累计请求数）走 `debug`；重试、接口降级与失败走 `warn`。
排查“日期为什么变了”时，按同一款游戏的行顺序读即可复现完整决策链。

## 11. 已知限制

- **终末地没有数值版本号**：条目只写“版本更新”；前瞻视频按标题关键词匹配，不按版本号。
- **动态接口不稳定**：常返回 `-352`/空列表，因此“官方明确前瞻公告”是增强项而非必需项；
  推算仍可给出 42 天节奏，终末地则回退到公告阶段更新日。
- **更新日当天 07:00 才发公告**：HoYo 账号在更新日 07:00 发布版本更新公告
  （绝区零 3.3 实测为 10-21 07:00）。在此之前刷新只能由上一版本的结束日推出当天版本；
  公告出现后自动切换到下一版本。后台 6 小时刷新最多晚 6 小时看到公告，
  需要即时性时手动刷新或交给周检 Agent。
- **发布渠道可能变化**：若某个账号改走动态/opus 而不是专栏，`x/space/article` 就不会
  出现该公告，插件只能靠上一版本结束日或 42 天节奏滚动；此时周检 Agent 负责补精确日期。
- **鸣潮官方前瞻视频搜不到**：只依赖官方合集接口；合集缺失时回退到周五规则。
- **B 站风控会变**：端点/`Referer`/限流阈值都可能在无预告的情况下调整。改动 `bilibili.js`
  前先用匿名请求复测；解析规则不联网，改端点不影响 `parse.test.mjs`。
- **前瞻日期在官方公布前只能推算**：卡片与描述都会标注“（推算）”，周检 Agent 负责在有
  官方预告后写回。预告通常集中在周三，故周检定在周三 10:00。
